# 2. Иерархия классов

```
Serializable                 интерфейс: save_binary/load_binary/save_text/load_text,
  │                          save/load/save_file/load_file
  └── Container              length(), empty(), clear(), type_name()
        ├── Sequence         values(), restore(), сериализация последовательностей
        │     ├── Array
        │     ├── SinglyList
        │     ├── DoublyList
        │     ├── Stack      (внутри SinglyList – композиция)
        │     ├── Queue      (внутри SinglyList – композиция)
        │     └── RBTree     (свой формат сохранения – метки 20(B))
        └── HashTable        put/get/remove/contains/for_each_pair/capacity/load_factor
              ├── ChainHashTable   метод цепочек
              └── OpenHashTable    открытая адресация: линейная или двойное хеширование
```

Идея: всё, что умеет сохраняться, – `Serializable`; всё, что хранит элементы, – `Container`. Последовательности (`Sequence`) сохраняются одинаково – списком значений, поэтому сериализация написана один раз в базовом классе, а каждый наследник реализует только два метода: `values()` (отдать все значения) и `restore()` (добавить одно значение при загрузке). Это паттерн «шаблонный метод». Хеш-таблицы сохраняют пары «ключ – значение», это сделано в `HashTable`.

Через указатель на базу можно работать с любым контейнером:

```cpp
std::vector<std::unique_ptr<Container>> all;
all.push_back(std::make_unique<Array>());
all.push_back(std::make_unique<RBTree>());
for (auto& c : all) c->save_file(c->type_name() + ".bin", Format::Binary);   // виртуальные вызовы
```

# 3. Все классы и методы (C++)

Обозначения: n – число элементов. Методы ЛР №1 возвращают `bool` (успех или нет), а результат передают через параметр-ссылку.

## 3.1 Serializable (`serializable.hpp/.cpp`)

Интерфейс сохранения. Полей нет, деструктор виртуальный.

| Метод | Что делает |
|---|---|
| `virtual void save_binary(ostream&) const = 0` | записать объект в бинарном формате (чисто виртуальный) |
| `virtual void load_binary(istream&) = 0` | прочитать из бинарного формата |
| `virtual void save_text(ostream&) const = 0` | записать в текстовом формате (JSON) |
| `virtual void load_text(istream&) = 0` | прочитать из JSON |
| `void save(ostream&, Format)` | выбрать `save_binary` или `save_text` по формату |
| `void load(istream&, Format)` | выбрать `load_binary` или `load_text` |
| `void save_file(path, Format)` | открыть файл (`std::ofstream`, binary) и вызвать `save`; если файл не открылся – `std::runtime_error` |
| `void load_file(path, Format)` | открыть файл на чтение и вызвать `load` |

`enum class Format : std::uint8_t { Binary, Text }` – формат файла.

## 3.2 Container и Sequence (`container.hpp`, `sequence.cpp`)

**Container** – абстрактный класс любого контейнера.

| Метод | Что делает |
|---|---|
| `virtual int length() const = 0` | число элементов |
| `bool empty() const` | `length() == 0` (общий для всех, не виртуальный) |
| `virtual void clear() = 0` | удалить все элементы |
| `virtual string type_name() const = 0` | имя типа (`"Array"`, `"RBTree"`…) – пишется в файл и проверяется при загрузке |

**Sequence** – контейнер значений.

| Метод | Что делает |
|---|---|
| `virtual Array values() const = 0` | все значения по порядку (массив – как есть, списки – от головы, стек – от вершины, дерево – ключи по возрастанию) |
| `protected virtual void restore(const string&) = 0` | добавить одно значение при загрузке |
| `save_binary` | заголовок (сигнатура, тип, число) + все `values()` как строки |
| `load_binary` | прочитать заголовок, проверить тип, прочитать **все** строки во временный `Array`, затем `clear()` и `restore()` каждой. Если данные испорчены, исключение вылетает до `clear()` – старое содержимое сохраняется |
| `save_text` | `codec::write_json(out, type_name(), values())` |
| `load_text` | `codec::read_json` → `clear()` → `restore()` каждого значения |

## 3.3 Array (`array.hpp/.cpp`) – динамический массив строк

Поля (private): `string* data` – буфер, `int size` – занято, `int capacity` – выделено (начально 4).

| Метод | Что делает | Сложность |
|---|---|---|
| `Array()` | буфер на 4 элемента | O(1) |
| `~Array()` | `delete[] data` | O(n) |
| `Array(const Array&)`, `operator=(const Array&)` | глубокое копирование (новый буфер, копия элементов); присваивание проверяет `this == &other` | O(n) |
| `Array(Array&&)`, `operator=(Array&&)` | перенос: забирает буфер у другого, тот становится пустым (`data = nullptr`, `capacity = 0`) | O(1) |
| `push_back(value)` | добавить в конец; если места нет – `resize()` | O(1) амортизированно |
| `insert(index, value)` | вставить по индексу 0…size, элементы справа сдвигаются; `false`, если индекс неверный | O(n) |
| `get(index, value&)` | прочитать по индексу с проверкой; `false` при выходе за границы | O(1) |
| `set(index, value)` | заменить по индексу с проверкой | O(1) |
| `erase(index, removed&)` | удалить по индексу, сдвиг влево, удалённое значение – в `removed` | O(n) |
| `length()` | `size` | O(1) |
| `at(index)` | элемент **без проверки** – быстрый доступ в циклах, где индекс заведомо верный | O(1) |
| `clear()` | `size = 0` (буфер остаётся) | O(1) |
| `private resize()` | новый буфер в 2 раза больше (если буфера нет – 4), перенос элементов | O(n) |

Удвоение даёт амортизированную O(1) для `push_back`: за n вставок копирований всего 4 + 8 + … + n < 2n.

## 3.4 SinglyList (`singly_list.hpp/.cpp`) – односвязный список

Поля: `Node* head`, `Node* tail`, `int count`; `struct Node { string value; Node* next; }` вложена и закрыта. Копирование и перенос запрещены (`= delete`), как в ЛР №1: список владеет узлами, случайная поверхностная копия привела бы к двойному удалению.

| Метод | Что делает | Сложность |
|---|---|---|
| `push_front(v)` | новый узел в голову | O(1) |
| `push_back(v)` | новый узел в хвост (есть указатель `tail`) | O(1) |
| `insert_after(key, v)` | вставить после первого узла со значением `key`; `false`, если нет | O(n) |
| `insert_before(key, v)` | вставить перед `key` (ищется предыдущий узел) | O(n) |
| `pop_front(removed&)` | удалить голову | O(1) |
| `pop_back(removed&)` | удалить хвост – нужно найти предпоследний узел | O(n) |
| `remove(key)` | удалить первый узел со значением `key` | O(n) |
| `get(i, value&)` | значение по индексу | O(n) |
| `contains(key)` | поиск значения | O(n) |
| `front(value&)` | значение головы | O(1) |
| `values()` | все значения от головы к хвосту | O(n) |
| `length()`, `clear()`, `type_name()` | методы ЛР №3 | O(1), O(n), O(1) |

## 3.5 DoublyList (`doubly_list.hpp/.cpp`) – двусвязный список

`Node { value, prev, next }`, поля `head`, `tail`, `count`. Закрытые помощники: `find(key)` – узел по значению, `unlink(node)` – исключить узел, перекинув `prev`/`next` соседей, и удалить его.

| Метод | Сложность |
|---|---|
| `push_front`, `push_back`, `pop_front`, `pop_back` | O(1) – оба конца доступны, предыдущий узел известен через `prev` |
| `insert_after(key, v)`, `insert_before(key, v)` | O(n) на поиск, сама вставка O(1) |
| `remove(key)`, `get(i, value&)`, `contains(key)` | O(n) |
| `values()` | O(n) |

Отличие от односвязного: `pop_back` и вставка перед узлом – O(1) после поиска, так как есть ссылка назад.

## 3.6 Stack и Queue (`stack.hpp/.cpp`, `queue.hpp/.cpp`)

Оба содержат закрытое поле `SinglyList list` – это **композиция** (стек «имеет» список, а не «является» им: наследование открыло бы лишние методы вроде `insert_after`).

| Stack | | Queue | |
|---|---|---|---|
| `push(v)` | `list.push_front(v)` – вершина в голове | `push(v)` | `list.push_back(v)` – в хвост |
| `pop(removed&)` | `list.pop_front` | `pop(removed&)` | `list.pop_front` – из головы |
| `top(value&)` | `list.front` | `front(value&)` | `list.front` |
| `values()` | от вершины ко дну | `values()` | от первого к последнему |

Все операции O(1), порядок LIFO у стека и FIFO у очереди. При загрузке стека `restore` делает `push_back`: значения сохранены от вершины ко дну, и каждое следующее должно лечь под предыдущее.

## 3.7 RBTree (`rb_tree.hpp/.cpp`) – красно-чёрное дерево (вариант ЛР №1)

Поля: `Node* nil` – общий чёрный лист-сторож вместо `nullptr`, `Node* root`, `int count`. `Node { key, red, left, right, parent }` с явным конструктором.

Свойства красно-чёрного дерева: 1) узел красный или чёрный; 2) корень чёрный; 3) листья (nil) чёрные; 4) у красного узла оба потомка чёрные; 5) на любом пути от узла до листьев одинаковое число чёрных узлов. Отсюда высота ≤ 2·log₂(n+1), и все операции – O(log n).

| Метод | Что делает |
|---|---|
| `insert(key)` | обычная вставка в дерево поиска, новый узел красный, затем `insert_fix`; `false`, если ключ уже есть |
| `erase(key)` | удаление (узел с двумя детьми заменяется следующим по порядку), затем `erase_fix`, если удалён чёрный узел; `false`, если ключа нет |
| `contains(key)` | поиск |
| `min_key(out&)`, `max_key(out&)` | крайний левый / правый узел |
| `next(key, out&)`, `prev(key, out&)` | следующий / предыдущий ключ по возрастанию |
| `keys()` | ключи по возрастанию (симметричный обход) |
| `preorder()`, `inorder()`, `postorder()`, `bfs()` | обходы, элементы с цветом, например `10(B)` |
| `diagram()` | рисунок дерева текстом (`|-- L:` / `` `-- R: ``) |
| `is_valid()` | проверка всех свойств: порядок ключей, нет двух красных подряд, одинаковая чёрная высота, корень чёрный, число узлов совпадает с `count` |
| `private static less(a, b)` | сравнение ключей: целые числа (до 18 цифр, можно с минусом) сравниваются как числа и идут раньше строк, остальное – как строки |
| `private left_rotate / right_rotate` | повороты – O(1) перестановка трёх указателей |
| `private insert_fix(z)` | восстановление свойств после вставки: дядя красный → перекраска и подъём вверх; дядя чёрный → один или два поворота и перекраска |
| `private erase_fix(x)` | восстановление после удаления чёрного узла: 4 случая по цвету брата и его детей |
| `private transplant(u, v)` | поставить поддерево v на место u |
| `private attach(key, red)` | ЛР №3: поставить узел на своё место **без** балансировки (для точной загрузки из файла) |
| `private load_labels(labels)` | ЛР №3: собрать временное дерево по меткам `20(B)` в прямом обходе, проверить `is_valid()`, и только потом обменять с текущим – при ошибке текущее дерево не меняется |

Почему дерево сохраняется прямым обходом с цветами, а не просто ключами: если загрузить ключи через `insert`, дерево пересобалансируется и может получить другую форму. Прямой обход (корень, левое, правое) позволяет вставить узлы ровно на свои места, а цвет из метки восстанавливает раскраску.

`values()` дерева – ключи по возрастанию, `restore(v)` – `insert(v)`.

## 3.8 Хеш-таблицы (`hash_table.hpp/.cpp`, из ЛР №2)

`hash_string(s)`: h = h·31 + код символа (mod 2⁶⁴, переполнение `uint64_t`). Полиномиальный хеш: учитывает порядок символов («ab» ≠ «ba»).

**HashTable** (абстрактный): `put(key, value)` – вставить или заменить, `true`, если ключ новый; `get(key)` → `std::optional<string>`; `remove(key)`; `contains(key)`; `for_each_pair(visit)` – обход всех пар; `capacity()`; `load_factor() = length / capacity`. Сериализация пар написана в базовом классе: бинарно – ключ и значение подряд, в JSON – `["k1", "v1", "k2", "v2"]` (при загрузке проверяется чётное число строк).

**ChainHashTable** – метод цепочек. Поля: `Entry** buckets_` (массив голов односвязных цепочек), `bucket_count_` (начально 8), `count_`. Индекс ячейки – `hash % bucket_count_`. Новая пара добавляется в голову цепочки. Если после вставки коэффициент заполнения станет больше 0,75, `rehash` удваивает число ячеек и раскладывает пары заново. `longest_chain()` – длина самой длинной цепочки (для анализа). Реализованы все пять специальных функций (правило пяти).

**OpenHashTable** – открытая адресация. Поля: `keys_`, `values_`, `cells_` (состояние ячейки: Empty / Busy / Deleted), `capacity_` – **простое** число (по умолчанию 11), `count_`, `deleted_`.

- i-я проба: `(h1 + i·step) mod m`, где h1 = H mod m; при линейном апробировании step = 1, при двойном хешировании step = 1 + H mod (m − 1). Так как m простое, любой шаг от 1 до m−1 обходит все ячейки.
- Удаление ставит «надгробие» (Deleted), а не Empty: иначе оборвалась бы цепочка проб, и ключи, стоящие дальше, перестали бы находиться. При вставке надгробие можно занять.
- Если (count + deleted + 1) / m > 0,75, `rebuild`: таблица увеличивается вдвое (до простого), если растёт число ключей, или перестраивается того же размера, чтобы вычистить надгробия.
- `probes(key)` – сколько ячеек просмотрено при поиске; `is_prime`, `next_prime` – статические помощники.

Линейное апробирование даёт **первичную кластеризацию**: занятые ячейки слипаются в длинные блоки. Двойное хеширование её избегает, потому что у разных ключей разный шаг.

| Операция | Среднее | Худшее |
|---|---|---|
| put, get, remove (обе таблицы) | O(1) | O(n) – все ключи в одной ячейке / одна длинная цепочка проб |
| rehash / rebuild | O(n), но редко → O(1) амортизированно на вставку |

## 3.9 codec (`codec.hpp/.cpp`) – чтение и запись форматов

Бинарные функции: `write_u32/read_u32` (4 байта, little-endian), `write_string/read_string` (длина u32 + байты; строка длиннее 64 МБ считается испорченной), `write_binary_header/read_binary_header` (сигнатура `L3B1`, имя типа, число элементов; проверка, что тип совпадает). Если данных не хватает – `std::runtime_error("unexpected end of binary data")`.

Текстовые функции – JSON из `file.cpp` ЛР №1, перенесены в анонимное пространство имён: `JsonString` (строка в кавычках с экранированием `"` `\` и управляющих символов `\u00XX`), `WriteItem`, `SkipSpaces`, `Expect`, `AddUtf8` (код `\uXXXX` → UTF-8), `ReadString`, `ReadValue` (строка или число без кавычек), `ParseJson`. Публичные: `write_json(out, type, values)` и `read_json(in, type)` – проверяет, что в файле ровно один ключ и это нужный тип.

# 4. Rust-версия

Те же сущности, но через трейты:

| C++ | Rust |
|---|---|
| абстрактный класс `Serializable` | `trait Serializable` (методы `save`, `load`, `save_file`, `load_file` – реализации по умолчанию в трейте) |
| `Container`, `Sequence`, `HashTable` | `trait Container: Serializable`, `trait Sequence: Container`, `trait HashTable: Container` |
| наследование реализации | общие функции `save_sequence_binary` и т. п. + макрос `impl_sequence_serializable!` |
| `private` поля | поля без `pub` (видны только внутри модуля) |
| исключение `runtime_error` | `Result<(), LoadError>`; `LoadError::Io` или `LoadError::Format` |
| `bool pop(string&)` | `fn pop(&mut self) -> Option<String>` |
| `unique_ptr<Container>` | `Box<dyn Container>` (динамическая диспетчеризация через vtable) |
| деструктор | `Drop` автоматически (память освобождает владелец) |

Списки из ЛР №1 хранят узлы в векторе `nodes: Vec<Option<Node>>`, связи – номера узлов (`Option<usize>`), освобождённые места – в `free`. Это обходит правила заимствования Rust без `unsafe`. Дерево хранит узлы в `Vec<Node>`, номер 0 – общий чёрный лист `NIL`. `#[derive(Clone)]` у дерева и таблиц даёт глубокое копирование. Clippy pedantic требует `Default` для структур с `new()` – добавлено.

# 5. Форматы файлов

**Бинарный** (все числа u32 little-endian):

```
4C 33 42 31          "L3B1" – сигнатура
05 00 00 00 Array    имя типа (длина + байты)
04 00 00 00          число элементов
02 00 00 00 31 30    элемент "10" (длина + байты)
...
```

У дерева элементы – метки `20(B)`, у таблиц – ключ и значение подряд.

**Текстовый** – JSON как в ЛР №1:

```
{
  "RBTree": ["20(B)", "10(B)", "5(R)", "15(R)", "30(B)", "25(R)"]
}
{
  "ChainHashTable": ["apple", "1", "plum", "3", "pear", "2"]
}
```

Загрузка всегда проверяет сигнатуру/структуру JSON, тип, длины; при любой ошибке – исключение, а содержимое контейнера не меняется (сначала всё читается, потом заменяется).

Бинарный формат быстрее (нет экранирования и разбора) и компактнее для чисел; текстовый читается человеком и переносим между программами. По бенчмарку Rust бинарная сериализация в 1,7–2,4 раза быстрее JSON.

# 6. Тесты, покрытие, бенчмарки, линтеры

**Генерация тестов.** Все три набора C++ строятся скриптом `tools/gen_tests.py` из одного описания: в описании проверки записаны строками `EQ(a, b)`, `TRUE(x)`, `FALSE(x)`, `THROWS(expr, Type)`, `NOTHROW(expr)`, а скрипт переводит их в макросы каждого фреймворка:

| Проверка | Boost.Test | Google Test | Catch2 |
|---|---|---|---|
| тест | `BOOST_AUTO_TEST_CASE(Name)` в `BOOST_AUTO_TEST_SUITE` | `TEST(Suite, Name)` | `TEST_CASE("Name", "[tag]")` |
| равенство | `BOOST_CHECK_EQUAL(a, b)` | `EXPECT_EQ(a, b)` | `CHECK(a == b)` |
| условие | `BOOST_CHECK(x)` | `EXPECT_TRUE(x)` | `CHECK(x)` |
| исключение | `BOOST_CHECK_THROW(e, T)` | `EXPECT_THROW(e, T)` | `CHECK_THROWS_AS(e, T)` |
| параметризованный | `BOOST_DATA_TEST_CASE(Name, data::make(cases), param)` | `TEST_P` + `INSTANTIATE_TEST_SUITE_P(..., ValuesIn(cases))` | `auto param = GENERATE(from_range(cases))` |

**Параметризованные тесты** – одно тело теста выполняется для каждого значения из таблицы параметров. Например, `Roundtrip` для каждого из 9 контейнеров и обоих форматов (18 запусков): создать заполненный контейнер → сохранить → загрузить в пустой → сравнить тип, длину и содержимое. Так же устроены `EmptyContainer` (9), `RejectsBadJson` (13 испорченных JSON), `RejectsBadTree` (5 неверных деревьев), операции хеш-таблиц (3 вида). Всего 33 теста, 78 запусков. В Rust то же сделано одной функцией `check_roundtrip(filled, make_empty, show)`, которая вызывается для каждого контейнера.

**Покрытие C++.** Сборка с флагом `--coverage` (CMake-опция `LAB3_COVERAGE`): компилятор добавляет счётчики, при компиляции появляются файлы `.gcno` (структура кода), при запуске тестов – `.gcda` (сколько раз выполнялась каждая строка). `gcovr` читает их и строит HTML: `gcovr --html -o coverage/index.html` (один файл с процентами по строкам, функциям, ветвлениям для каждого исходника). Всё это делает `cpp/scripts/coverage.sh`.

**Покрытие Rust.** `RUSTFLAGS="-C instrument-coverage"` → `cargo test` создаёт `.profraw` → `llvm-profdata merge` объединяет их в `.profdata` → `llvm-cov show -format=html > coverage/index.html` (один файл с подсветкой строк). Скрипт `rust/scripts/coverage.sh`. Альтернатива – утилита `cargo llvm-cov --html`.

**Бенчмарки.** Google Benchmark: функция `BM_...(benchmark::State& state)` с циклом `for (auto _ : state)`, `benchmark::DoNotOptimize` не даёт компилятору выбросить результат, `->Range(100, 100000)->Complexity()` – прогон на разных n и оценка асимптотики. Rust: свой бенчмарк на `std::time::Instant`, медиана повторов, `std::hint::black_box`.

**Линтеры.** clang-tidy – статический анализатор C++ (группы bugprone, clang-analyzer, cppcoreguidelines, misc, modernize, performance, readability; проверяются и заголовки). Исправлено: инициализация полей в теле конструктора → значения по умолчанию / список инициализации; `const` для неизменяемых переменных; `[[nodiscard]]` для методов, результат которых нельзя игнорировать; `static`-функции → анонимное пространство имён; явные перемещающие операции у классов с деструктором; ложные срабатывания анализатора на узлах дерева (явный конструктор `Node`). Clippy pedantic с `-D warnings`: `let … else` вместо `match` с `return`, `Default` для структур с `new()`.

# 8. Ответы на вопросы к защите

## Классы. Секции. Конструкторы, списки инициализации

Класс объединяет данные и операции над ними. Секции доступа: **public** – внешний интерфейс, доступен всем; **private** – только методам самого класса (в `class` по умолчанию); **protected** – классу и наследникам. Пример: у `Array` поля `data`, `size`, `capacity` и метод `resize()` закрыты, операции `push_back`, `get` открыты; `restore()` в `Sequence` – protected, его вызывает базовый класс при загрузке, но не пользователь.

Конструктор вызывается при создании объекта и приводит его в корректное начальное состояние. Виды: по умолчанию, с параметрами, копирующий `Array(const Array&)`, перемещающий `Array(Array&&)`. **Список инициализации** инициализирует поля до входа в тело конструктора: `Array::Array() : data(new string[4]) {}`, `RBTree::RBTree() : nil(new Node{...}), root(nil) {}`. Он обязателен для `const`-полей, ссылок, базовых классов и полей без конструктора по умолчанию, и эффективнее присваивания в теле (нет лишней инициализации по умолчанию). Поля инициализируются в порядке **объявления в классе**, а не в порядке списка – поэтому у дерева `nil` объявлен раньше `root`.

## Деструкторы и время жизни. Константность методов

Деструктор вызывается при уничтожении объекта и освобождает ресурсы: `~Array()` делает `delete[] data`, `~SinglyList()` удаляет все узлы, `~RBTree()` удаляет узлы и `nil`. Время жизни: автоматический объект (на стеке) – до конца блока; динамический (`new`) – до `delete`, при `unique_ptr` – пока жив владелец; статический – до конца программы. Деструкторы базовых классов **виртуальные** (`virtual ~Serializable() = default`), иначе `delete` через указатель на базу не вызвал бы деструктор наследника (утечка). Правило пяти: если класс сам управляет ресурсом (нужен деструктор), нужно определить или запретить копирование и перемещение – у `Array` они реализованы, у списков и дерева запрещены (`= delete`).

Константный метод (`int length() const`) обещает не менять объект; его можно вызывать у константного объекта и по константной ссылке. Компилятор запрещает в нём изменять поля (кроме `mutable`).

## Порядок конструирования. Шаблоны классов

Конструирование: сначала базовые классы (от самого верхнего: `Serializable` → `Container` → `Sequence`), затем поля в порядке объявления, затем тело конструктора. Разрушение – в обратном порядке: тело деструктора, поля, базовые классы. Поэтому в конструкторе и деструкторе базы виртуальные функции ведут себя как функции базы – наследник ещё не создан или уже разрушен (clang-tidy об этом предупреждал, вызовы были убраны).

Шаблон класса – заготовка, по которой компилятор генерирует класс для конкретного типа: `template <typename T> class DynArray { T* data; ... };`, `DynArray<int>`, `DynArray<string>`. Код генерируется при инстанцировании, поэтому определение шаблона обычно в заголовке. В ЛР №2 использовался `DynArray<T>`; в ЛР №3 контейнеры хранят строки, а разнообразие типов достигается иерархией и полиморфизмом. Примеры шаблонов в проекте – `std::unique_ptr<Container>`, `std::optional<std::string>`.

## Хеш-функции. Свойства, требования, коллизия

Хеш-функция отображает данные произвольной длины в значение фиксированного размера. Требования для хеш-таблиц: детерминированность (один ключ – один хеш), быстрота вычисления, равномерное распределение по ячейкам, зависимость от всех частей ключа. **Коллизия** – разные ключи с одинаковым хешем (или индексом ячейки); по принципу Дирихле они неизбежны, если ключей больше, чем значений. Способы разрешения: цепочки (`ChainHashTable`) и открытая адресация (`OpenHashTable`). В проекте `hash_string`: h = h·31 + c mod 2⁶⁴.

## Элементарные способы построения хеш-функций. Классификация. Криптографические

Элементарные: **деление** h(k) = k mod m (m – простое, не степень двойки); **умножение** h(k) = ⌊m·{k·A}⌋, 0 < A < 1 (Кнут: A ≈ 0,618); **полиномиальный** хеш строки Σ cᵢ·pⁱ mod M; **свёртка** (сложение или XOR частей ключа); **середина квадрата**. Классификация: некриптографические (для таблиц: полиномиальный, FNV, MurmurHash, xxHash) и криптографические; также универсальное хеширование (функция выбирается случайно из семейства), совершенное (без коллизий для известного набора ключей).

Криптографические требования: стойкость к поиску прообраза (по h нельзя найти x), ко второму прообразу (по x нельзя найти другой x' с тем же хешем), к коллизиям, лавинный эффект. Современные: **SHA-2** (SHA-256, SHA-512), **SHA-3** (Keccak), **BLAKE2/BLAKE3**, российский **«Стрибог»** (ГОСТ Р 34.11-2012, 256/512 бит). MD5 и SHA-1 устарели – для них найдены коллизии.

## Применение хеш-функций в криптографии

Проверка целостности (контрольная сумма файла); электронная подпись (подписывается хеш сообщения, а не всё сообщение – ГОСТ Р 34.10-2012 + Стрибог); коды аутентификации HMAC (хеш с секретным ключом); хранение паролей (только медленные функции с солью: Argon2, bcrypt, scrypt, PBKDF2 – чтобы перебор был дорогим); выработка ключей (KDF); блокчейн и доказательство работы; деревья Меркла. Полиномиальный хеш из проекта для этого **непригоден**: коллизии для него легко подобрать.

## Принципы объектной модели

- **Абстрагирование** – выделение существенного: `Container` описывает «что умеет любой контейнер», не говоря как.
- **Инкапсуляция** – сокрытие реализации: узлы, буферы, счётчики закрыты, менять их можно только через методы, которые сохраняют корректность (например, `count` всегда равен числу узлов).
- **Модульность** – разбиение на модули: каждый класс в своей паре `.hpp/.cpp`, Rust – отдельные модули.
- **Иерархия** – наследование (Array «является» Sequence) и агрегация/композиция (Stack «имеет» SinglyList).
- **Типизация** – строгий контроль типов: нельзя передать `RBTree` туда, где ждут `HashTable`; enum class `Format` нельзя спутать с числом.
- **Параллелизм** – способность объектов работать одновременно; контейнеры проекта не потокобезопасны – для общего доступа нужна внешняя синхронизация (`std::mutex`).
- **Сохраняемость** – объект переживает программу: `save_file`/`load_file`.

## Экземпляры класса. Уровни доступа. Классификация методов

Экземпляр (объект) – конкретная переменная класса со своим состоянием: `Array a; a.push_back("x");`. Статические члены общие для всех экземпляров (`OpenHashTable::is_prime`). Уровни доступа – public, protected, private; `friend` даёт доступ отдельной функции или классу. Классификация методов: конструкторы и деструкторы; селекторы/«геттеры» (`length`, `get`, `contains` – `const`, не меняют объект); модификаторы (`push_back`, `insert`, `clear`); итераторы/обходы (`values`, `preorder`, `for_each_pair`); виртуальные и чисто виртуальные (`= 0`); статические (без `this`: `less`, `next_prime`); закрытые вспомогательные (`resize`, `rehash`, `insert_fix`).

## Средства UML. Нотация класса, взаимодействия, иерархия

Класс – прямоугольник из трёх частей: имя, атрибуты, операции. Видимость: `+` public, `-` private, `#` protected; абстрактные класс и методы – курсивом; стереотипы `«interface»`, `«enumeration»`. Отношения:

- **обобщение (наследование)** – сплошная линия с пустым треугольником к базе (Array → Sequence);
- **реализация интерфейса** – пунктир с пустым треугольником (в Rust-диаграмме структуры реализуют трейты);
- **композиция** – сплошная линия с закрашенным ромбом у целого (Stack ◆— SinglyList: список не существует без стека);
- **агрегация** – пустой ромб (часть может существовать отдельно);
- **ассоциация** – простая линия, **зависимость** – пунктирная стрелка `«use»` (RBTree использует Array, все используют codec).

Иерархия показывается деревом обобщений сверху вниз (или справа налево, как в `uml_cpp.png`).

## Интерфейс и абстрактный класс

Интерфейс – только контракт: набор операций без данных и реализации. В C++ – класс из одних чисто виртуальных функций (`Serializable` почти такой: плюс общие невиртуальные `save`/`load`); в Rust – `trait`. Абстрактный класс – класс хотя бы с одной чисто виртуальной функцией; создать объект нельзя, но он может хранить данные и реализовывать часть методов (`Sequence` реализует всю сериализацию). Сравнение: интерфейс задаёт «что», абстрактный класс – «что» и частично «как»; класс может реализовать много интерфейсов, а множественное наследование реализации сложнее (проблема ромба). В проекте каждый класс наследует одну цепочку.

## Наследование

Механизм создания класса на основе существующего: наследник получает поля и методы базы и может добавлять свои и переопределять виртуальные (`override`). Виды в C++: public (отношение «является», интерфейс базы остаётся открытым – используется в проекте), protected, private (наследование реализации). Множественное и виртуальное наследование (против дублирования общей базы). Принцип подстановки Лисков: объект наследника должен работать везде, где ожидается база, – любой `Sequence` можно сохранить через `Serializable&`. Где наследование неуместно, используется композиция: стек не наследует список, иначе у стека появились бы `insert_after` и `remove`.

## Полиморфизм. Виртуальные методы. sizeof при наследовании

Полиморфизм – один интерфейс, разное поведение. Статический: перегрузка функций, шаблоны (выбор на этапе компиляции). Динамический: виртуальные функции – реализация выбирается во время выполнения по фактическому типу объекта: `c->type_name()` через `Container*` вернёт `"RBTree"` для дерева. `override` проверяет, что метод действительно переопределяет виртуальный; `final` запрещает дальнейшее переопределение; чисто виртуальный метод `= 0` делает класс абстрактным.

sizeof объекта наследника ≥ sizeof базы + собственные поля + выравнивание. У полиморфного класса (есть виртуальные функции) в объекте обычно есть скрытый указатель на таблицу виртуальных функций (vptr) – 8 байт на 64-битной системе; он один на объект при одиночном наследовании и добавляется в каждый полиморфный подобъект при множественном. Пример: `Array` = vptr (8) + `string*` (8) + два `int` (4 + 4) = 24 байта. Пустой класс имеет sizeof ≥ 1 (у объектов разные адреса), но пустая база в наследнике может занимать 0 байт (empty base optimization). `sizeof(Container*)` – размер указателя (8), а не объекта. Точные числа стандарт не фиксирует – это решение ABI компилятора.

## Таблица виртуальных функций

vtable – массив адресов виртуальных функций, по одному на каждый полиморфный класс (создаётся компилятором). Каждый объект хранит vptr – указатель на vtable своего класса; его устанавливает конструктор (поэтому в конструкторе базы vptr указывает на таблицу базы). Вызов `c->length()` компилируется в: взять vptr из объекта → взять из таблицы адрес по номеру функции → вызвать. Цена – одно-два обращения к памяти и невозможность встраивания (inline). В Rust аналог – «толстый» указатель `&dyn Trait`: указатель на данные + указатель на vtable. Это модель реализации (Itanium ABI, MSVC), стандарт C++ её не требует.

## Сериализация и десериализация. Применение. Форматы

Сериализация – преобразование объекта в последовательность байт или текст для хранения или передачи; десериализация – восстановление объекта. Применение: сохранение в файлы и БД, передача по сети (клиент–сервер, микросервисы), кэширование, обмен между языками, снимки состояния. Форматы: **текстовые** – JSON, XML, YAML, CSV, TOML (читаемы, переносимы, но больше и медленнее); **бинарные** – собственные (как `L3B1`), Protocol Buffers, MessagePack, CBOR, BSON, Cap'n Proto (компактны и быстры, но нечитаемы человеком). Важные вопросы: порядок байт (в проекте явно little-endian), версия формата, проверка входных данных (повреждённый или вредоносный файл) – в проекте проверяются сигнатура, тип, длины и для дерева – все его свойства.

## Понятие тестирования. Цели

Тестирование – проверка соответствия программы требованиям путём её выполнения (динамическое) или анализа (статическое) на специально подобранных данных. Цели: найти дефекты как можно раньше (исправление дешевле); убедиться, что требования выполнены (верификация) и продукт нужен пользователю (валидация); дать информацию о качестве для принятия решений; предотвратить дефекты (раннее участие в анализе требований). Тестирование показывает наличие ошибок, но не доказывает их отсутствие.

## Стандарты тестирования, основные показатели

Международные: ISO/IEC/IEEE 29119 (понятия, процессы, документация, техники тестирования), IEEE 829 (документация), ISO/IEC 25010 (модель качества). Российские: ГОСТ Р 56920-2024, 56921-2016, 56922-2016 (на основе 29119), ГОСТ 34.603-92 (испытания АС), ГОСТ 19.301-79 (программа и методика испытаний), ГОСТ Р 71207-2024 (статический анализ). Показатели: покрытие кода (строки, ветвления, функции), покрытие требований, число и плотность дефектов (на 1000 строк), доля пройденных тестов, процент найденных до выпуска дефектов (DRE), время выполнения тестов, плотность замечаний анализатора. В работе: 100 % пройденных тестов, покрытие строк C++ ≈ 98 %, 0 замечаний линтеров.

## Поддерживаемость по ISO 25010

Сопровождаемость (поддерживаемость) – насколько эффективно продукт можно изменять: исправлять, улучшать, адаптировать. Подхарактеристики: **модульность** (изменение одного компонента минимально влияет на другие – отдельные классы и файлы), **возможность многократного использования** (структуры ЛР №1 использованы в ЛР №2 и №3, `SinglyList` внутри стека и очереди), **анализируемость** (легко найти причину ошибки и оценить последствия изменения – линтеры, понятные имена, UML), **модифицируемость** (изменение без внесения дефектов – общий код сериализации в базовом классе меняется в одном месте), **тестируемость** (легко задать критерии и провести тесты – маленькие классы, покрытие ≥ 85 %). В редакции ISO/IEC 25010:2023 состав сопровождаемости не изменился; действующий ГОСТ Р ИСО/МЭК 25010-2015 соответствует редакции 2011 года.

## ISTQB

International Software Testing Qualifications Board – международная некоммерческая организация (с 2002 г.), которая разрабатывает учебные программы (syllabus) и единый глоссарий терминов тестирования и проводит сертификацию тестировщиков через национальные советы (в России – RSTQB). Уровни: Foundation (CTFL – основы: принципы, процесс, уровни и виды, техники тест-дизайна, управление тестированием, инструменты), Advanced (Test Analyst, Technical Test Analyst, Test Manager), Expert, а также специализации (Agile, автоматизация, производительность, безопасность, AI). Значение: общий язык терминов и признаваемый стандарт квалификации.

## Основные виды тестирования

| Признак | Виды |

| Уровень | модульное, интеграционное, системное, приёмочное |
| Знание кода | белый ящик, чёрный ящик, серый ящик |
| Запуск кода | статическое (обзоры, анализаторы), динамическое |
| Объект | функциональное; нефункциональное – производительности, нагрузочное, стрессовое, безопасности, удобства, совместимости, надёжности |
| Цель запуска | дымовое (smoke), повторное (re-test), регрессионное |
| Данные | позитивное, негативное |
| Автоматизация | ручное, автоматизированное |
| Исполнитель | альфа (внутри), бета (пользователи) |

В работе: модульное (тесты каждого класса), интеграционное (сохранение и загрузка через иерархию), белый ящик с покрытием, позитивные и негативные (пустые структуры, неверные индексы, испорченные файлы), производительности (бенчмарки), статическое (линтеры), автоматизированное регрессионное (`ctest`, `cargo test` одной командой).

## Основные принципы тестирования (ISTQB)

1. Тестирование показывает наличие дефектов, а не их отсутствие.
2. Исчерпывающее тестирование невозможно – нужен выбор тестов по рискам и техникам (классы эквивалентности, граничные значения).
3. Раннее тестирование экономит время и деньги.
4. Скопление дефектов: большинство ошибок – в небольшом числе модулей.
5. Парадокс пестицида: одни и те же тесты перестают находить новые ошибки – их нужно обновлять.
6. Тестирование зависит от контекста (банковское ПО и игра тестируются по-разному).
7. Заблуждение об отсутствии ошибок: программа без дефектов может не решать задачу пользователя.

## Уровни тестирования

- **Модульное (unit)** – отдельная функция или класс в изоляции: `Array::insert` на границах индексов. Пишет разработчик, выполняется за миллисекунды.
- **Интеграционное** – взаимодействие модулей: `Sequence::save_binary` + `codec` + `RBTree::load_labels`; тест `Roundtrip`.
- **Системное** – вся программа целиком по требованиям: `lab3_demo` сохраняет и загружает все контейнеры.
- **Приёмочное** – готовность к сдаче заказчику: проверка преподавателем по заданию.

Чем выше уровень, тем дороже найденный дефект, поэтому большинство тестов – модульные («пирамида тестирования»).

## Почему не рекомендуют, чтобы тестированием занимались программисты

Речь о независимом тестировании системы, а не о юнит-тестах. Автор кода психологически настроен доказать, что программа работает, а не найти ошибки; он повторяет в тестах свои же неверные предположения (если неправильно понял требование, тест проверит неправильное поведение); знание реализации подсказывает «удобные» данные; у разработчика нет взгляда пользователя; конфликт интересов при сроках. Поэтому Майерс формулирует принцип: программист не должен тестировать свою программу, а организация – свои проекты. При этом модульные тесты разработчик писать **должен** – он лучше всех знает границы и инварианты кода (TDD); независимый тестировщик дополняет, а не заменяет их.

## Юнит-тестирование в C++: Boost Test Library и Google Test

**Boost.Test**: `#define BOOST_TEST_MODULE lab3_boost` + `#include <boost/test/unit_test.hpp>` (генерирует `main`); тесты группируются `BOOST_AUTO_TEST_SUITE(Name)` … `BOOST_AUTO_TEST_SUITE_END()`; тест – `BOOST_AUTO_TEST_CASE(Name)`; проверки `BOOST_CHECK(x)`, `BOOST_CHECK_EQUAL(a, b)`, `BOOST_CHECK_THROW(e, T)`, `BOOST_REQUIRE_*` (прерывает тест); параметризованный – `BOOST_DATA_TEST_CASE(Name, data::make(cases), param)`; фикстуры `BOOST_FIXTURE_TEST_CASE`. Подключение в CMake: `find_package(Boost REQUIRED COMPONENTS unit_test_framework)`.

**Google Test**: `#include <gtest/gtest.h>`, `main` даёт библиотека `gtest_main`; тест – `TEST(Suite, Name)`; фикстура – класс от `::testing::Test` и `TEST_F`; параметризованный – класс от `TestWithParam<T>`, `TEST_P`, `GetParam()`, `INSTANTIATE_TEST_SUITE_P`; проверки `EXPECT_*` (продолжить при ошибке) и `ASSERT_*` (прервать тест): `EXPECT_EQ`, `EXPECT_TRUE`, `EXPECT_THROW`, `EXPECT_NO_THROW`. В CMake: `find_package(GTest REQUIRED)`, `target_link_libraries(tests_gtest GTest::gtest_main)`, `add_test(...)`. Запуск всех наборов – `ctest`.

Catch2 (третий фреймворк): `TEST_CASE("name", "[tag]")`, `CHECK`, `REQUIRE`, `SECTION`, `GENERATE`; `Catch2::Catch2WithMain`.

## Юнит-тестирование в Rust

Встроенное, без сторонних библиотек: модуль `#[cfg(test)] mod tests { use super::*; ... }` рядом с кодом (компилируется только при `cargo test`, видит закрытые элементы); функция-тест помечается `#[test]`; проверки `assert!(cond)`, `assert_eq!(a, b)`, `assert_ne!`; ожидание паники – `#[should_panic]`; тест может возвращать `Result`. Интеграционные тесты – файлы в папке `tests/` (видят только публичный API крейта): `tests/structures.rs`, `tests/serialization.rs`. Запуск: `cargo test` (все), `cargo test имя` (фильтр). Бенчмарки – `benches/`, `cargo bench` (у нас свой, без `criterion`). Сторонние фреймворки: `rstest` (параметризованные тесты, фикстуры), `proptest`/`quickcheck` (тесты свойств на случайных данных), `mockall` (заглушки), `criterion` (бенчмарки), `cargo-nextest` (быстрый запуск). Для Go: встроенный пакет `testing` (`func TestX(t *testing.T)`, `go test -cover`) и `testify` (`assert.Equal`).

## Порядок создания HTML-отчёта о покрытии в C++

1. Собрать проект с инструментированием: `-O0 -g --coverage` (= `-fprofile-arcs -ftest-coverage`) для компилятора и компоновщика; в проекте – `cmake -DLAB3_COVERAGE=ON -B build-cov`. При компиляции рядом с объектными файлами появляются `.gcno`.
2. Удалить старые `.gcda`, запустить тесты (`tests_boost`, `tests_gtest`, `tests_catch2`) – при выполнении пишутся `.gcda` со счётчиками.
3. Построить отчёт: `gcovr -r . --filter src/ --filter include/ --html -o coverage/index.html --print-summary` (`--html-details` – отдельная страница на файл). Альтернатива: `lcov --capture -d build-cov -o cov.info` и `genhtml cov.info -o coverage`.
4. Открыть `coverage/index.html`: проценты строк, функций и ветвлений по каждому файлу.

Всё это выполняет `cpp/scripts/coverage.sh`.

## Порядок создания HTML-отчёта о покрытии в Rust (и Go)

Rust, вариант 1 – `cargo install cargo-llvm-cov`, затем `cargo llvm-cov --html` → `target/llvm-cov/html/index.html`. Вариант 2 (в проекте, `rust/scripts/coverage.sh`): `RUSTFLAGS="-C instrument-coverage" cargo test` → файлы `.profraw`; `llvm-profdata merge -sparse *.profraw -o merged.profdata`; `llvm-cov show <исполняемые файлы тестов> -instr-profile=merged.profdata -format=html > coverage/index.html`; сводка – `llvm-cov report`. Третий вариант – `cargo tarpaulin --out Html`.

Go: `go test -coverprofile=coverage.out ./...`, затем `go tool cover -html=coverage.out -o coverage.html`.
